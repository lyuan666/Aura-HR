**Embedding 降维数据迁移方案**:

维度从 2048 改为 ≤1536 后，老向量和新向量在 pgvector 中**完全不兼容**（维度不一致直接报错，不是计算不准）。

```
前置确认: 是否有需要保留的 embedding 数据？
  ├── 没有（开发期）→ TRUNCATE embedding 列，直接切换，跳到 Phase 4
  └── 有（已有生产数据）→ 执行完整迁移流程
```

完整迁移流程（4 phase）:
```sql
-- Phase 1: 加新列（不影响现有功能）
ALTER TABLE candidates ADD COLUMN embedding_v2 vector(1536);
ALTER TABLE job_positions ADD COLUMN embedding_v2 vector(1536);

-- Phase 2: 应用层 batch job 重新生成向量
-- 后端提供 POST /api/admin/migrate-embeddings 端点
-- 分批加载: 每次 100 条有 embedding 的记录 → 用新模型重新生成 → 写入 embedding_v2
-- 端点支持: ?cursor=xxx&batchSize=100

-- Phase 3: 验证 + 切换列（维护窗口执行）
-- 3a. 确认 embedding_v2 行数 = embedding 行数
-- 3b. 切换
ALTER TABLE candidates DROP COLUMN embedding;
ALTER TABLE candidates RENAME COLUMN embedding_v2 TO embedding;
ALTER TABLE job_positions DROP COLUMN embedding;
ALTER TABLE job_positions RENAME COLUMN embedding_v2 TO embedding;

-- Phase 4: 建 HNSW 索引（向量搜索核心）
CREATE INDEX idx_candidates_embedding ON candidates USING hnsw (embedding vector_cosine_ops);
CREATE INDEX idx_jobs_embedding ON job_positions USING hnsw (embedding vector_cosine_ops);
```

async semanticSearch(query: string, tenantId: string) {
  const queryEmbedding = await this.embeddingService.generateEmbedding(query);
  return this.candidateRepo.query(
    `SELECT *, embedding <=> $1 AS distance
     FROM candidates

matching.service.ts findBestMatches（两阶段检索）:
```typescript
// 之前: take 200 + 内存余弦相似度 + +0.1 造假
// 之后: Phase 1 pgvector 粗筛 + Phase 2 应用层精排
async findBestMatches(jobId: string, tenantId: string) {
  const job = await this.jobRepo.findOne({ where: { id: jobId, tenantId } });
  if (!job?.embedding) throw new NotFoundException('职位向量未生成');

  // Phase 1: pgvector HNSW 索引粗筛 (O(log N))
  // 取 100 个语义最相似的，留余量给 Phase 2 精排
  const candidates = await this.candidateRepo.query(
    `SELECT *, 1 - (embedding <=> $1) AS semantic_score
     FROM candidates
     WHERE embedding IS NOT NULL
       AND tenant_id = $2
       AND status IN ('new', 'active', 'in_process')
     ORDER BY embedding <=> $1
     LIMIT 100`,
    [JSON.stringify(job.embedding), tenantId]
  );

  // Phase 2: 应用层精排 (O(1)，只有 100 条)
  const scored = candidates.map(c => {
    const tagScore = this.calculateTagOverlap(job.skillTags || [], c.parsed_tags?.skills || []);
    const expScore = this.calculateExperienceMatch(job, c);
    const semantic = parseFloat(c.semantic_score) || 0;
    const hardMultiplier = this.calculateHardMatch(job, c);

    const totalScore = (semantic * 0.5 + tagScore * 0.3 + expScore * 0.2) * hardMultiplier * 100;

    return { candidate: c, score: Math.round(totalScore) };
  });

  return scored
    .filter(r => r.score > 30)
    .sort((a, b) => b.score - a.score)
    .slice(0, 20);
}
```

**为什么两阶段**：如果试图把 tagMatch/experienceMatch 塞进 SQL ORDER BY，
pgvector 的 HNSW 索引用不上，变成全表扫描。两阶段分离后，Phase 1 走索引，
Phase 2 在应用层只处理 100 条候选人的纯计算，不涉及数据库查询。

### Step 3: 持久化任务队列 + 向量化流水线

**目标**: 向量化完成后触发匹配推送，进程崩溃不丢失任务

**风险（已修复）**：纯 EventEmitter 是内存态的，进程崩溃/重启/部署时所有未处理事件丢失。
后果：候选人"沉底"（数据库有记录但永远没有 embedding，永远匹配不到任何职位）。

**方案：数据库持久化队列 + EventEmitter 实时触发 + cron 补偿**

三层保障：
1. **持久化队列**：pending_jobs 表存储所有待处理任务，崩溃后可恢复
2. **EventEmitter**：实时触发，正常情况下秒级响应
3. **Cron 补偿**：每 5 分钟扫描"超时未完成"的任务，补偿处理

**新增文件**:
- `apps/api/src/entities/pending-job.entity.ts` — 持久化任务表
- `apps/api/src/modules/queue/queue.service.ts` — 任务队列服务
- `apps/api/src/modules/queue/queue.module.ts`
- `apps/api/src/modules/candidate/candidate.service.ts` — 候选人入库时写入 pending_job + emit 事件
- `apps/api/src/modules/matching/matching.listener.ts` — 监听事件，处理向量化 + 匹配
- `apps/api/src/app.module.ts` — 确保 EventEmitterModule.forRoot()

**持久化任务表定义**:
```typescript
@Entity('pending_jobs')
export class PendingJobEntity {
  @PrimaryGeneratedColumn('uuid') id: string;
  @Column() type: string;           // 'vectorize' | 'match_push'
  @Column({ type: 'jsonb' }) payload: Record<string, any>;
  @Column({ default: 'pending' }) status: string;  // pending/processing/completed/failed
  @Column({ default: 0 }) attempts: number;
  @Column({ name: 'max_attempts', default: 3 }) maxAttempts: number;
  @Column({ name: 'next_retry_at', type: 'timestamp', nullable: true }) nextRetryAt: Date;
  @Column({ name: 'tenant_id', nullable: true }) @Index() tenantId: string;
  @Column({ name: 'error_message', type: 'text', nullable: true }) errorMessage: string;
  @CreateDateColumn({ name: 'created_at' }) createdAt: Date;
  @UpdateDateColumn({ name: 'updated_at' }) updatedAt: Date;
}
```

**任务处理流程**:
```
候选人入库
    │
    ├── 1. 写入 pending_job (type='vectorize', status='pending')
    ├── 2. emit('candidate.created', { candidateId, tenantId })
    │
    ▼ (正常路径: EventEmitter 实时触发)
    VectorizeListener.onCandidateCreated()
    ├── pending_job.status = 'processing'
    ├── 调用 EmbeddingService 生成向量
    ├── 成功: pending_job.status = 'completed', emit('candidate.vectorized')
    └── 失败: pending_job.attempts++, status='pending', next_retry_at = now + 5min
    
    ▼ (补偿路径: Cron 每 5 分钟，多实例安全)
    QueueService.retryStuckJobs()
    └── SELECT * FROM pending_jobs
        WHERE status IN ('pending', 'processing')
          AND (next_retry_at IS NULL OR next_retry_at <= NOW())
          AND attempts < max_attempts
        ORDER BY created_at ASC
        LIMIT 20
        FOR UPDATE SKIP LOCKED  ← 多实例不会抢到同一批任务

    ▼ (向量化完成后)
    candidate.vectorized 事件
    │
    ├── 写入 pending_job (type='match_push', status='pending')
    └── emit('candidate.vectorized') → MatchPushService 处理匹配推送
```

**多实例部署安全（SELECT FOR UPDATE SKIP LOCKED）**

当 API 服务器扩展到 2+ 实例（或 K8s 多 Pod），多个实例的 cron 同时扫 pending_jobs 表：
- 没有 SKIP LOCKED → 两个实例拿到相同的任务 → 同一条简历生成两次向量 → 顾问收到重复通知
- 有 SKIP LOCKED → 每个实例只拿到别人没锁住的行 → 天然分片，无竞争

```sql
-- QueueService.claimBatch() 实现
async claimBatch(limit = 20): Promise<PendingJobEntity[]> {
  return this.manager.transaction(async (txn) => {
    // 批量锁定并取任务（其他实例看不到这些行）
    const jobs = await txn.query(`
      SELECT * FROM pending_jobs
      WHERE status IN ('pending', 'processing')
        AND (next_retry_at IS NULL OR next_retry_at <= NOW())
        AND attempts < max_attempts
      ORDER BY created_at ASC
      LIMIT $1
      FOR UPDATE SKIP LOCKED
    `, [limit]);

    if (jobs.length === 0) return [];

    // 立即标记为 processing，释放锁
    const ids = jobs.map(j => j.id);
    await txn.query(`
      UPDATE pending_jobs
      SET status = 'processing', attempts = attempts + 1
      WHERE id = ANY($1)
    `, [ids]);

    return jobs;
  });
}
```

不需要 Redis，不需要额外的分布式锁服务，PostgreSQL 原生解决。
即使现在单实例部署，代码写对了以后扩容不需要改。

### Step 6: PDF 推荐报告服务

**PDF 生成方案: pdfmake（声明式文档定义 API）**

**为什么不用 Puppeteer**：headless Chrome 每实例占 100-200MB 内存。猎头场景下顾问可能批量
生成推荐报告（比如同时给甲方推 5 个候选人），3 个并发 PDF = 600MB。会把简历解析等其他
关键服务的内存挤爆。

**为什么选 pdfmake 而不是 pdfkit**：pdfmake 底层同样依赖 pdfkit，但在 npm 上作为独立包
存在，提供了声明式文档定义 API（doc-definition）。推荐报告是固定模板的结构化文档，
pdfmake 的声明式写法（类似 HTML 的嵌套结构）比 pdfkit 手动算坐标更易维护。

```
方案对比:
┌─────────────┬──────────────┬──────────────┬────────────────────┐
│ 方案         │ 内存/请求     │ 开发体验      │ 隐私风险            │
├─────────────┼──────────────┼──────────────┼────────────────────┤
│ pdfmake     │ ~10MB        │ 声明式，类似HTML│ 无（纯本地）         │
│ pdfkit      │ ~10MB        │ 手动算坐标     │ 无（纯本地）         │
│ @react-pdf │ ~30MB        │ JSX 模板      │ 无（纯本地）         │
│ Puppeteer   │ 100-200MB    │ 完整 CSS      │ 无                  │
│ 外部服务     │ 0            │ 完整 CSS      │ 简历数据发到第三方   │
└─────────────┴──────────────┴──────────────┴────────────────────┘
```

### Step 10: 匹配算法重设计（两阶段检索）

**目标**: 去掉 +0.1 造假，设计合理的多维评分体系

**修改文件**:
- `apps/api/src/modules/matching/matching.service.ts`

**核心架构：两阶段检索（避免全表扫描）**

```
Phase 1 (数据库层 - pgvector HNSW 索引):
  ├── 利用 HNSW 索引，O(log N) 时间复杂度
  ├── 只用语义相似度排序，取 top-100 粗筛
  └── SQL: ORDER BY embedding <=> $jobEmbedding LIMIT 100

Phase 2 (应用层 - 纯内存计算):
  ├── 输入: Phase 1 返回的 100 个候选人
  ├── 计算: tagMatchScore + experienceMatch (纯 CPU，无 DB 查询)
  ├── 融合: 加权求和得到最终分数
  └── 输出: sort by totalScore → take top 20
```

**为什么不能把所有维度塞进一条 SQL**：
```sql
-- 反例：这个查询 pgvector HNSW 索引用不上
SELECT *, (1 - embedding <=> $1) * 0.5 + tag_overlap(...) * 0.3 + exp_score(...) * 0.2 AS total
FROM candidates ORDER BY total DESC  -- HNSW 索引失效，全表扫描
```
`ORDER BY total DESC` 不是 `ORDER BY embedding <=> $1`，pgvector 的 HNSW 索引用不上，
退化为全表扫描。两阶段分离后各自利用最优策略。

**新评分公式 (Phase 2 应用层)**:
```
totalScore = (semanticScore * 0.5 + tagMatchScore * 0.3 + experienceMatch * 0.2) * hardMatchMultiplier * 100
```

各维度计算：
- `semanticScore`: Phase 1 pgvector 返回的 cosine similarity (0-1)
- `tagMatchScore`: JD skillTags 与候选人 parsedTags.skills 的交集率 (0-1)
- `experienceMatch`: 多因素综合评分
  ```
  experienceMatch = (
    industryMatch(c.currentCompany 归属行业 vs JD 行业) * 0.4 +
    salaryFit(c.expectedSalary vs job.salaryRange) * 0.3 +
    yearsFit(c.totalYears vs job 最低年限要求) * 0.3
  )
  ```
- `hardMatchMultiplier`: 薪资差距 > 1.5x → 0.5 乘数（降权不剔除）

**去掉 +0.1**: 最低分为 0，不做人为保底。不够好的匹配得 0 分是合理的。

**Phase 1 LIMIT 的选择**: 取 100 而非最终需要的 20，因为语义 top-100 里可能有
tagMatch/experienceMatch 更好的候选人不在语义 top-20 里。100 是召回率与性能的平衡点。

**依赖**: Step 2 (pgvector), Step 3 (持久化队列)

### Step 11: 匹配主动推送（含通知聚合）

**目标**: 新候选人入库后自动匹配现有 JD，推送匹配结果给顾问

**新增文件**:
- `apps/api/src/modules/matching/match-push.service.ts`
- `apps/api/src/modules/matching/matching.listener.ts` (如果 Step 3 没创建)

**通知轰炸问题（已设计缓解方案）**:

场景：顾问一次性批量上传 50 份简历 → 50 个向量化完成 → 50 条匹配推送 → 顾问手机炸了。

解决方案：**租户维度的通知聚合**。匹配结果先暂存在内存缓冲区，定时（5 分钟）汇总为 1 条通知推送。

```
批量上传 50 份简历
    │
    ▼
50 个向量化任务完成 → 逐个触发匹配
    │
    ▼
匹配结果暂存到通知缓冲区（按租户分组）
    │
    ▼  每 5 分钟定时 flush（或缓冲区达到 50 条时立即 flush）
    │
    ▼
汇总为 1 条通知:
"您上传的 50 份简历已完成解析，系统找到 12 个高匹配候选人。
  其中 3 人与「高级前端工程师」匹配度超过 80%。点击查看详情 →"
```

**实现**:
```typescript
class MatchPushService {
  // 租户维度的通知缓冲区
  private notificationBuffer: Map<string, MatchNotification[]> = new Map();
  private readonly FLUSH_INTERVAL_MS = 5 * 60 * 1000; // 5 分钟
  private readonly FLUSH_THRESHOLD = 50; // 50 条立即 flush

  async onCandidateVectorized(candidateId: string, tenantId: string) {
    const matches = await this.findMatchesForCandidate(candidateId, tenantId);
    if (matches.length === 0) return;

    // 不立即推送，而是暂存到缓冲区
    const buffer = this.notificationBuffer.get(tenantId) || [];
    buffer.push({ candidateId, matches, timestamp: Date.now() });
    this.notificationBuffer.set(tenantId, buffer);

    // 达到阈值立即 flush（防止批量上传时缓冲区无限增长）
    if (buffer.length >= this.FLUSH_THRESHOLD) {
      await this.flushTenantNotifications(tenantId);
    }
  }

  // 每 5 分钟执行一次：汇总所有租户的缓冲通知
  @Cron('*/5 * * * *')
  async flushAllNotifications() {
    for (const [tenantId, notifications] of this.notificationBuffer) {
      if (notifications.length === 0) continue;
      await this.flushTenantNotifications(tenantId);
    }
  }

  private async flushTenantNotifications(tenantId: string) {
    const notifications = this.notificationBuffer.get(tenantId) || [];
    if (notifications.length === 0) return;

    const summary = this.summarize(notifications);
    // 当前: 创建 RecommendationEntity + console.log
    // 未来: 推送到微信/消息中心
    await this.sendNotification(tenantId, summary);
    this.notificationBuffer.set(tenantId, []);
  }
}
```

**依赖**: Step 3 (持久化队列), Step 10 (新匹配算法)
