## Problem Statement

中国中小猎头公司使用 Excel/WeChat 手动管理整个业务流程，效率极低。现有 ATS 系统（Moka、北森、谷露等）面向企业 HR 部门设计，不适合猎头业务模型（BD→寻访→匹配→面试→Offer→过保→开票）。YZSCHROS 旨在成为专门为猎头公司打造的人才智能平台，而不仅仅是 ATS。

## Demand Evidence

- 有具体的猎头顾问在等待产品完成
- 这些顾问目前使用 Excel/WeChat 管理业务，工作流非常痛苦
- 痛点真实但尚未量化（缺少"每天花多少小时手动操作"的具体数字）
- **待验证：** 需要量化顾问每天在手动简历录入和信息整理上花费的时间

## Status Quo

猎头顾问的日常工作流：
- 简历通过微信/邮件收到后，手动将关键信息录入 Excel
- 用 Excel 表格管理候选人状态（谁在面试、谁拿到了 Offer）
- 候选人匹配完全依赖顾问的经验和记忆
- 过保期跟踪靠日历提醒或遗忘
- 开票流程手动计算、手动记录

## Target User & Narrowest Wedge

**目标用户：** 中小型猎头公司的猎头顾问（Consultant），每天处理大量简历，需要快速入库和匹配。

**最窄切入点：** 简历解析入库 + 候选人看板管道。两阶段体验：正则+启发式提取在 <1s 返回基础信息（姓名、电话、邮箱），LLM 深度解析在 10-15s 内流式返回结构化履历。让顾问愿意录入更多简历，积累人才库。

**但创始人揭示了更大的愿景：** 人才库的规模是核心资产。足够大的人才库 → AI 人才模型（岗位能力画像、市场画像）→ 数据产品卖给甲方企业。这是一个数据飞轮。

## Constraints

- 基于现有项目规划：需求管理、客户管理、人才管理、人才看板、合同管理等模块不变
- 产品规划以当前项目为主
- 技术架构可以做重构优化
- 技术栈：Next.js 15 + NestJS 10 + TypeORM + PostgreSQL（现有代码库实际版本，非项目介绍书中的目标版本）

## Premises

1. **猎头公司会为专门为他们设计的系统付费** — 不是用通用 ATS 的缩水版。猎头业务模型（过保期、服务费比例）与 HR 招聘完全不同。
2. **简历解析是基础能力，不是差异化** — 人才库规模 + AI 人才模型才是真正的护城河。解析速度是让顾问愿意录入更多简历的催化剂，但价值在于数据沉淀后的智能应用。
3. **目标用户是中小型猎头公司** — 不是大型猎头如 Michael Page。中小型猎头最需要效率工具，也最容易被忽视。

## Cross-Model Perspective

独立 AI 审查的关键洞察：

1. **最强版本：** 猎头原生操作系统，用 AI 解析作为入口，BD→开票完整管道作为锁定。没有现有中国 ATS 专门服务猎头管道。
2. **最关键发现：** 用户用 Excel 管理一切，说明产品必须比现有工作流更简单更快，不是更强大。"比粘贴到 Excel 更少的点击"。
3. **挑战了 Premise #2：** 简历解析已经是标配，真正的护城河是过保期管理和开票流程。
4. **创始人反驳：** 简历解析只是最基础的。猎头的痛点是尽可能获取更多简历建立庞大人才库。人才库的规模效应可以做岗位能力画像、市场画像，这些人才模型未来可以卖给甲方。合同/开票是更好的工具，猎头的本质是解决人才需求。

**修正后的 Premise #2：** 简历解析是基础能力（让数据进来的入口），**人才库规模 + AI 人才模型**才是飞轮。

## Approaches Considered

### Approach A: 最小可行入口
- 简历粘贴/上传 + AI 解析入库
- 候选人看板管道（6 个阶段）
- 基础搜索
- 先给 2-3 个顾问用，收集反馈
- **Effort:** S (human: ~2周 / CC: ~1天)
- **Risk:** Low
- **Pros:** 最快验证，最快收集真实反馈
- **Cons:** 缺少架构层面的设计，后期扩展可能需要大量重构

### Approach B: 人才智能平台架构 (CHOSEN)
- 从数据飞轮完整视角设计
- 基于现有模块升级架构
- 三个里程碑交付
- **Effort:** L (human: ~2月 / CC: ~1周)
- **Risk:** Med
- **Pros:** 架构正确，支持飞轮效应，未来扩展成本低
- **Cons:** 前期需要更多架构设计

### Approach C: 数据产品优先
- 不做 ATS，直接做人才数据产品
- **Effort:** M (human: ~1月 / CC: ~3天)
- **Risk:** High — 没有 ATS 作为数据入口，数据来源不足
- **Pros:** 直接验证数据产品的商业价值
- **Cons:** 没有猎头顾问使用就没有数据，没有数据就没有产品

## Recommended Approach

**Approach B: 人才智能平台架构** — 基于现有项目规划升级。

核心思路：保留现有产品模块（需求管理、客户管理、人才管理、人才看板、合同管理），但在技术架构层面做三件事：

### 里程碑 1: 数据入口 + 基础管道 (2-3 周)
- 简历极速解析入库（mammoth/pdf-parse + LLM 结构化提取）
- **注意：** 现有 CandidateEntity 状态枚举为 `new/active/in_process/offered/placed/inactive`，需扩展为猎头业务管道：`new → sourced → recommended → interviewing → offered → guarantee → placed`。涉及数据库迁移和 API 契约更新。
- 基础搜索（关键字 + 简单过滤）
- **交付标准：** 2-3 个顾问能用它替代 Excel 管理日常候选人

### 里程碑 2: 智能匹配 + 人才画像 (3-4 周)
- JD 解析 + AI 人岗匹配（向量匹配 + 关键字匹配混合）
- **注意：** 现有 MatchingService 使用内存余弦相似度（top-200 截断），需升级为 pgvector 数据库级向量搜索，否则人才库规模增长后会崩溃。
- 岗位能力画像生成（基于人才库数据）
- 候选人 AI 评估报告（定义评估维度、设计 prompt 模板、构建 UI 展示组件）
- 企业客户管理 + 合同管理
- **新增实体：** GuaranteeTrackingEntity（入职日期、过保期限、到期日期、状态），支持过保期自动跟踪和提醒
- **交付标准：** 顾问输入一个 JD，系统推荐前 5 个候选人，顾问通过 accept/reject 按钮反馈，至少 3 个被认可

### 里程碑 3: 全业务闭环 + 数据飞轮验证 (4-6 周)
- 全业务链路闭环（BD → 开票）
- 市场人才报告生成（行业/岗位维度的市场分析）— **先用人工方式为甲方制作 1-2 份报告验证付费意愿，再决定是否自动化**
- 过保期自动跟踪和开票触发
- **交付标准：** 猎头顾问能在系统内完成从 BD 到开票的完整业务流程

### 未来阶段: 数据产品 (需先验证甲方付费意愿)
- 人才模型数据产品 MVP
- 甲方企业门户
- **前提条件：** 里程碑 3 中人工制作的报告验证了甲方愿意付费

### 技术架构升级要点

1. **数据层：** 现有 CandidateEntity 的 JSONB 字段（parsedTags、workExperiences、projectExperiences、educationHistory、careerExpectations）需要统一 schema 规范，确保 AI 分析输入一致性
2. **AI 层：** 现有 AiService 已实现双引擎路由（本地 Qwen + 云端 GLM-4 + 信号量限流）。需要重构为：接口抽象层（便于测试和切换模型）+ 两阶段解析（正则即时提取 + LLM 深度结构化）
3. **搜索层：** 现有 MatchingService 使用内存余弦相似度（top-200 截断），已有 embedding 列。需要升级为 pgvector 数据库级向量搜索，解决规模化问题
4. **数据产品层：** 预留 API 接口，为甲方企业数据产品做准备（放在未来阶段）

## Open Questions

1. 猎头顾问每天在手动操作上花多少时间？（需量化）
2. 具体是哪个顾问、在哪家公司？（需锁定具体用户）
3. 甲方企业是否愿意为人才市场报告付费？价格敏感度？
4. 本地 LLM vs API 调用的成本对比？（猎头场景下解析精度要求可能更高）

## Success Criteria

1. **里程碑 1：** 2-3 个顾问用系统替代 Excel 管理日常候选人，日活跃
2. **里程碑 2：** 输入 JD 后，系统推荐的前 5 个候选人中至少 3 个被顾问认可
3. **里程碑 3：** 至少 1 个甲方企业愿意为市场人才报告付费或试用

## The Assignment

**这周做一件事：** 去找一个具体的猎头顾问。坐在他旁边，看他用 Excel 管候选人。不要指导，不要建议，就是看。记下：他在哪个步骤最慢？在哪个步骤骂了一句？在哪个步骤关掉了窗口？这些就是你产品的优先级。
